# ADR 0004: Activity-процес надсилання розв'язку

## Контекст

UC-03 має валідацію, асинхронний `pending`, фінальний результат і захист від
дублювання. Sequence-моделі лабораторної №3 показують повідомлення, але не
дають єдиного потоку дій із ролями та fork/join.

## Рішення

Описати процес одним Mermaid `flowchart` з swimlanes для Learner, Submission
API і Test Runner Service. Створювати одну `Attempt`, паралельно повідомляти
про `pending` і dispatch-ити ту саму `attemptId`, а після результату розгалужувати
`passed` та `failed`.

## Розглянуті альтернативи

1. `stateDiagram-v2` — відхилено, бо ролі та дії були б менш явними.
2. Дві окремі діаграми для SC-03 і SC-04 — відхилено, бо вимога просить одну
   точну форму для одного бізнес-процесу.
3. Окремі `Submission`/`TestRun` — відхилено, бо це суперечить ER-моделі.

## Наслідки

Процес має повні переходи та видиму асинхронність, але не моделює внутрішню
чергу runner, push-механізм або retry UC-08.
